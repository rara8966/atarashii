# 建设用地报批审查报告 Demo 说明

## 1. 我对这个项目的理解

这个项目不是单纯写一份审查报告，也不是简单做一个上传文件的页面。它真正要解决的是：把建设用地报批里分散、复杂、容易漏项的政策要求，变成一套可以一步步填、一步步检查、最后自动生成报告的系统。

旧目录里的页面和报告模板已经把方向讲得很清楚：系统围绕 1009 号文的审查报告格式，把整个流程拆成八步：项目基本情况、申请用地现状、农用地转用、补充耕地、土地征收、土地利用、地灾压矿、信访违法。每一步都对应一批材料、一些固定字段、一些政策风险点。

这次 Demo 的目标就是先做出一个闭环：用户把材料拖进来，系统先用 Tika 解析文字，再用政策明白卡和内置规则做初筛，最后调用本机 Ollama 给出“哪里要改、哪里可补、哪里有风险”的人话建议，并把结果合并进报告预览。

## 2. 当前 Demo 已经能演示什么

当前 Demo 使用真实样例“兴宁五塘风电场一期工程”的数据，不再使用旧页面里的演示假数据。

已内置的关键数据包括：项目总用地面积 0.3800 公顷，农用地 0.3800 公顷，耕地和永久基本农田均为 0，征收集体土地 0.0236 公顷，使用国有土地 0.3564 公顷，违法用地 0.0588 公顷且已处罚整改到位。

页面现在可以演示这些能力：

1. 八步审查导航，每一步显示本步骤目标、重点检查项和建议材料。
2. 明白卡单独上传，本步骤材料单独上传，避免用户分不清政策材料和报件材料。
3. 拖拽或选择上传 PDF、Word、TXT 等材料。
4. 后端用 Apache Tika 抽取上传材料文本。
5. 系统识别材料类型，例如审查报告样稿、预审批复、征收材料、违法用地材料等。
6. 自动抽取项目名称、预审批复、核准文号、面积、生态红线、占用耕地、压覆矿产等字段。
7. 每一步按“已做到、需确认、未通过、待补”展示审查状态。
8. 抽取出来的字段可以在页面手工修改，修改后会先保存到本地状态库。
9. 根据政策明白卡和 1009 号文审查口径做规则检查。
10. 支持本机 Ollama，也支持在页面临时配置 DeepSeek API Key 调用大模型。
11. 一键生成报告预览，并导出 `.md` 和 `.docx`。

## 3. AI 在这里负责什么

AI 不直接替代审批人员下结论，也不把涉密材料传到外网。

这版 Demo 的 AI 主要做三件事：

1. 帮用户快速读材料，提炼当前材料讲了什么。
2. 帮项目经理看“这一步还有哪些地方可能需要改”。
3. 把政策语言转成更容易理解的提示，方便客户现场演示。

真正需要严肃判断的内容，仍然由规则、材料原文和人工复核共同确认。这个定位比较稳，也更适合后面接真实数据。

## 4. 明白卡怎么用

根目录的 `2025重大项目用地政策明白卡.pdf` 已经接入后端。上传材料分析时，后端会读取明白卡内容，再根据当前步骤挑出相关片段作为规则和 AI 提示依据。

为了避免 Demo 首次上传时被大文件拖慢，1009 号文目前采用“内置审查口径摘要”的方式参与判断。也就是说：明白卡是真实读取，1009 号文先用稳定摘要托底。后续如果要做生产版，可以把 1009 号文拆成结构化知识库，而不是每次上传都重新解析整份大 PDF。

## 5. 模型选择

本机检测到两个 Ollama 模型：

- `qwen25vl-7b-local:latest`
- `qwen25vl-3b-local:latest`

用户电脑是 RTX 4060，所以默认优先用 7B，效果会更好；如果 7B 响应慢或超时，系统会自动降级到 3B，保证 Demo 不会卡死。

实际自测中，真实报告上传分析时 7B 超时后成功 fallback 到 3B，页面正常展示了 AI 建议。

本轮也增加了 DeepSeek 配置窗口。Key 只保存在浏览器本地，不写进代码、不提交到项目文件。演示时选择 DeepSeek 后，上传材料会由前端把 Key 临时发给本机后端，再由后端调用 DeepSeek 接口返回分析结果。

## 6. 代码大概怎么做的

项目放在 `policy-report-demo` 目录，分成前后端两部分。

后端在 `backend`：

- `DemoController` 提供接口：项目样例、Ollama 状态、文档分析、报告生成。
- `TikaDocumentParser` 负责解析上传文件和政策文件。
- `DocumentAnalysisService` 是核心流程：解析文本、识别材料、抽字段、跑政策检查、调用 Ollama。
- `PolicyKnowledgeService` 负责读取明白卡，并按步骤提取相关政策片段。
- `OllamaClient` 负责调用本机 Ollama，并处理 7B 到 3B 的降级。
- `DemoProjectService` 内置兴宁五塘真实样例和八步审查底稿。
- `ReportGenerationService` 负责把样例数据和上传分析结果拼成报告草稿。
- `WorkspaceStateService` 是本轮新增的轻量状态库，负责把每一步字段、检查项、上传分析结果保存到 `backend/data/workspace-state.json`。
- `DeepSeekClient` 是本轮新增的大模型接口，走 DeepSeek 的 OpenAI 兼容接口。
- 报告导出现在支持 Markdown 和 Word Docx 两种格式。

前端在 `frontend`：

- React + Vite 做一个三栏工作台。
- 左侧是八步审查导航。
- 中间是拖拽上传、AI 分析结果和报告预览。
- 右侧是真实样例底稿、本步骤重点、建议材料。
- 页面会显示 Ollama 状态，让演示时能说明“本地模型已接上”。

UI 上参考了 Python-island 的一些感觉：轻量卡片、状态胶囊、本地优先的表达方式。但 Python-island 是 PySide6 桌面项目，不是 React 项目，所以这里只借鉴风格和产品思路，没有直接搬代码。

## 8. 下一步建议

这版已经适合拿来演示“闭环思路”。下一步如果要继续推进，我建议按这个顺序做：

1. 把八步的每一步材料清单和字段清单做成配置，不写死在代码里。
2. 把 1009 号文和明白卡拆成结构化知识库，按步骤、材料、规则精确检索。
3. 接 Word 模板导出，生成真正可下载的审查报告。
4. 增加人工修改区，让 AI 抽取字段后可以人工确认、改值、留痕。
5. 增加“缺材料清单”和“退件风险清单”，让系统更像报件体检工具。
6. 等拿到更多真实报件后，补充字段识别和规则判断的样例测试。

当前 Demo 的重点不是做完所有业务细节，而是证明这条路是通的：政策文件、真实材料、AI 分析、规则检查、报告生成可以串成一条可演示的产品闭环。

## 9. 本地启动方式

推荐用 VS Code 的 Run Task：

```text
Terminal -> Run Task -> policy-report: dev
```

也可以分别启动：

```text
Terminal -> Run Task -> policy-report: backend
Terminal -> Run Task -> policy-report: frontend
```

手工命令如下。

后端启动：

```powershell
cd F:\atarashii\policy-report-demo\backend
mvn spring-boot:run
```

前端启动：

```powershell
cd F:\atarashii\policy-report-demo\frontend
fnm env | Invoke-Expression
fnm use 18
npm run dev -- --host 127.0.0.1
```

浏览器访问：

```text
http://127.0.0.1:5173/
```
